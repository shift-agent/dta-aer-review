Two brands, one roof

One WordPress install. One inventory. Two brands that look nothing alike — resolved per request, themed by preset, and scoped at the catalog query.

How a request becomes a brand

Brand is resolved once, early, then everything downstream reads it. No conditional branching scattered through templates.

Verified three ways:
1. One source — both catalogs render from one template + one structural stylesheet. Component census is identical; the only differences are the documented section variants (hero, CTA) and DTA's script flourish.
2. ss-launch conformance — the 22 --shell-* tokens consumed by base.css were checked against ss-launch's own emitters: 22/22 exist. All 7 section types used (nav-standard, hero-fullbleed, hero-split, showcase-grid, cta-dark, cta-banner, footer-standard) already exist in the SSLA registry — nothing new was invented. Hit toggle SSLA sections on either catalog to see them labelled.
3. Shared inventory — both sites render the same 26 products, grouped from 205 flat Current RMS size listings, with real names and real photography.
4. Multi-page & functional — home, collection, product detail and quote basket per brand. Live search, category filters, size selection and a working quote basket.

Where each piece lives

Respecting existing ownership — chrome stays with the theme; the engine only recommends.

ss-theme

Chrome

Header, nav, footer. Owned by the theme, dressed by the active brand preset. Not reinvented in the engine.

ss-launch

Brand registry

Create a brand, bind its domain, pick its preset and menus, preview. Plus the per-page “which brand” control.

ss-workspace

Operating surface

Day-to-day content and catalog work, with brand-context switching while editing.

new bolt-on

Inventory

Current RMS connector, canonical mapping, variation overrides, brand assignment, image pipeline, scheduled sync.
